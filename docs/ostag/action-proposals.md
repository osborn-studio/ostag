# Frozen Brief action proposals (B01)

Status: library and maintenance foundation. Release/audit receipts are tracked outside this document. This module does not install a production route, register a provider executor, enable a Brief flag, or establish live acceptance. B02/U02/B03 remain required before effects can run.

## Host contract

`ActionProposalService` uses the existing `RevisionService`, `ApprovalService` and `RunLedger`. The host must authenticate `RequesterContext` and independently implement the current `observe`, `authorize` and private `destination` callbacks. Deserialized identifiers, model output and type validation do not grant access. Authorization must return exactly `True`.

A `FieldObservation` binds the requester, original Feishu resource, record, field, typed old value, provider version, source snapshot digest and grant revision. An absent field must be rejected by the adapter, never represented as a null value. The snapshot SHA is content evidence, not a provider CAS/version token. Unsupported provider version semantics must fail closed in the adapter.

A `FrozenFieldChange` adds the typed new value, job, currently adopted revision, original root digest, existing run identifier stable host/UI `proposal_id`, and `ledger_epoch` from `RunLedger.frozen_epoch()` (initially `initial`). The run identifier must use the existing `run_` command grammar. The host owns run provenance. Use the same `proposal_id` when editing the same logical action, even if its target or payload changes; do not derive it from target/payload or let an untrusted client choose a new slot to evade replacement.

`propose(scope, change)` rechecks the current adopted revision, grant, observation and private destination before and after creation. Adoption is content confirmation only: a new receipt still needs approval. A racing withdrawal can leave an unapproved historical proposal; a failed post-check does not return it as current.

`propose(scope, edited_change, replaces=previous_action_id)` atomically creates the replacement and marks its predecessor stale in one authoritative ledger event. A competing edit using the same predecessor loses. Applying/applied/failed/blocked predecessors cannot be replaced because their effects may be uncertain. Exact replay returns the existing receipt and its current state, including stale, without resetting approval.

`resolve(scope, action_id)` reloads the authoritative receipt and validates its complete frozen intent and current context. It is a read/validation operation, not permission to execute later: the future apply path must check again at the effect boundary and supply provider concurrency controls and effect journaling.

## Compatibility and persistence

The existing `ActionReceipt` wire schema is unchanged. Frozen receipts use the reserved `action_frozen` prefix followed by the digest, compatible with the existing command parser. Their target system is `brief_field_change`; no executor is registered here. Canonical JSON is stored as a string inside the existing payload to preserve null, empty, false and zero values through legacy pruning. Secret-like strings and nonfinite/oversized/deeply nested JSON are rejected.

The existing JSONL ledger remains authoritative; there is no separate approval database. Cooperating legacy append writers acquire a shared blocking lock; frozen creation and state transitions acquire the exclusive lock on the same inode. This preserves legacy wait semantics without giving legacy writes a new bounded-admission failure. A stuck live lock owner can still delay those writes. Frozen creation performs strict history validation, verifies the original binding and synchronizes the file and parent directory before returning. Retry after a failed synchronization repeats synchronization before claiming durable creation. State transitions compare the authoritative prior state under the same lock, so cached approval/apply state cannot resurrect a superseded proposal.

Provision the ledger parent directory before admitting proposals. Frozen lock admission fails after a bounded 0.5-second wait; legacy append admission waits for the owner. Strict proposal reads stream the entire history and retain receipt-related records only, so there is no whole-file 64 MiB lockout. Malformed or ambiguous history fails closed until explicit recovery. Legacy empty payloads and unrelated nonfinite diagnostic values retain their pre-existing semantics; strict finite JSON is enforced for frozen records and recovery markers. Scans remain linear in file size, and individual records/receipt history can still consume substantial memory; indexing and compaction remain operational debt. This is a local cooperative-file contract: external file replacement, noncooperating writers, network-filesystem lock semantics, rotation and large-ledger indexing are not provided. Binding hashes detect accidental drift; they are not signatures against an actor who controls the ledger file.

## Verification boundary

The fixed B01 gate covers immutable values, existing command approval, replay, corruption, independent processes, failed fsync recovery, revocation, changed revisions, competing replacements and stale cached apply. Additional existing ledger/approval caller suites cover compatibility. Exact source hashes and actual Claude CLI model receipts are stored outside the repository in the task runtime. Test and static audit evidence must remain separate from Linux/full CI, formal GitHub approval and production acceptance.

## Recovery procedure and uncertainty

Recovery is a trusted local maintenance operation, not an authenticated HTTP endpoint. Stop effect workers and all clients using older binaries first. Preserve an immutable incident copy and its SHA256, including any malformed bytes. Call `recover_frozen_history(expected_sha256=..., operator=Principal(...), reason=...)` only with the exact inspected current-file digest. A changed file is refused under the same exclusive inode lock. The method neither replaces the file nor truncates bytes: it appends a delimiter if needed, followed by a recovery marker in the existing `security_event` envelope, then synchronizes file and directory.

The marker binds the entire preceding byte prefix and operator/reason to a fresh recovery epoch. Strict reads can quarantine malformed history only when this prefix binding validates. Every earlier known frozen receipt becomes blocked; old cached state cannot apply. An old-epoch proposal whose creation was hidden in damaged bytes cannot be newly inserted. New unrelated proposals require the new epoch and still start with no approval. A blocked logical action whose predecessor survived strict parsing cannot be re-proposed merely by changing its epoch or attempt. Records between the first corruption point and its recovery marker are not treated as trustworthy parsed history; their identities may be unknown, so their logical slots require incident reconciliation before reuse. The raw incident bytes remain available for reconciliation.

This is availability recovery for proposal admission, not evidence that an external effect was absent, successful or safe to retry. Unknown provider effects require B03/U02 reconciliation before any related new action or resumed execution. This library has no provider executor and must not be wired to a generic write executor without those gates. Backup rollback is not supported as an approval recovery path. Do not bypass blocked state by inventing new job/proposal identities.

A crash before the recovery marker is complete leaves damaged history denied. If a formerly complete JSON event was only missing its newline, adding that delimiter preserves that entire event rather than discarding it. A completed marker blocks prior approvals even if the caller failed to receive its acknowledgement. Another recovery may conservatively create another epoch; it never restores approval. Frozen state transitions synchronize before returning, so an apply caller cannot proceed after a reported durability failure.
