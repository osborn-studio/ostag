# Automatic routing fallback — design only (Phase 6)

**Status: DESIGN. Nothing in this document is implemented, flagged on,
scheduled, or deployed.** Phase 6 of the v0.3→v0.4 upgrade authorizes a
design document only (handoff §10). Any runtime change requires a new,
separately authorized phase gated on the explicit owner approval described
in §9 below.

## 1. What "automatic fallback" would mean in OStag

Today the relay router (`CopilotRelayService`) is deterministic with a
single candidate: the quoted envelope's session, else the principal's
current session. When that session is unusable, routing **fails closed**
and a human re-selects. Automatic fallback would let the router re-route
an ordinary instruction to a *newer session of the same task* when the
selected session has become terminal — and nothing more. This is a far
narrower capability than upstream OpenTag Phase 3's placement selector
(which Phase 5 deliberately did not port), and it stays narrower on
purpose.

What the shipped substrate actually provides (stated precisely):

- **RoutingDecision** (Phase 5) records candidates, eligibility reasons,
  and the selected route for every decision — the audit vocabulary. Its
  recording is **best-effort by design**; §6 explains why automatic
  decisions need a stronger guarantee.
- **HumanEscalation** (Phase 4) provides time-bounded human decisions where
  expiry never authorizes — the notification/escalation substrate.
- **CompletionContract** (Phase 1/2) distinguishes "agent responded" from
  "work completed with evidence" — the success-metric substrate.
- **AgentAccessProfileSnapshot** (Phase 3) is **shadow-only observability**:
  it records empty permissions, a system-principal requester, and a
  non-resolving policy placeholder. It does **not** freeze which human may
  reach which session and plays **no authorization role** here.
  `RelayPolicy` + `IdentityStore` remain the only authorization
  authorities, exactly as today.

## 2. Scope: the single permitted fallback

Fallback applies to exactly one situation:

> An **ordinary instruction** (`instruction.send`) targets the principal's
> current session, and that session is **terminal**
> (`completed`/`failed`/`cancelled`), and a **newer non-terminal session of
> the same `task_id` on the same instance** exists.

Everything else stays fail-closed, explicitly including:

- **`stale_decision_version` / decision answers** — decision answers are
  bound to the exact `(instance, runtime, session, turn, session_version)`
  identity and the store's atomic update requires all fields to match;
  re-routing one to another session cannot preserve the decision's
  identity. Fail-closed, permanently, unless a future design specifies a
  safe rebinding protocol (out of scope here).
- **`no_current_session`** — there is no failed primary to derive intent
  from; the existing picker flow is the correct behavior.
- **`access_denied`** — an authorization failure must remain a failure.
- **Policy gates** (`requires_approval` / `requires_confirmation`) — human
  gates, not routing failures. Messages classified `requires_approval` are
  never eligible for fallback even after approval.
- **`duplicate_event`**, snapshots, proposal confirmations — unchanged.

## 3. Candidate constraints and deterministic preference order

Candidate pool (all constraints AND-ed):

- same `task_id` **and** same `instance_id` as the failed primary — the
  user's explicit task selection is preserved; fallback never crosses
  tasks or instances;
- session state non-terminal;
- principal authorized for the instance via the **live**
  `RelayPolicy.can_access` (the same call the router makes today — no new
  authorization surface);
- write-gating unchanged: canary session allow-lists and `write_enabled`
  apply to the fallback target exactly as to a directly selected session.

Preference order (total, pure): most recent `updated_at`, tie-break on
lexicographic `(runtime_id, session_id)`. The selector must be a pure
function of (failed primary, candidate rows) so the RoutingDecision
explanation reproduces it exactly and "selected equals the actual route"
stays provable.

If the pool is empty, behavior is identical to today: fail closed, and the
existing controller flow (picker / error message) proceeds unchanged.

## 4. Failure and fallback semantics

- **One hop.** If the fallback target fails for any reason, the attempt
  fails closed; no cascading.
- Every fallback emits a `RoutingDecision` with reason code
  `auto_fallback` (new vocabulary entry) whose candidates include the
  failed primary (ineligible, `session_terminal`) and the chosen target
  (eligible, new candidate code `same_task_successor`, with the preference
  rule recorded in the reason message).
- Every fallback opens a **non-blocking** Phase 4 `HumanEscalation`
  (class `reconciliation`, audience `work_item_owner`, dedupe key
  `fallback:{task_id}`) so a human always sees that a machine re-routed;
  deduped so a noisy task doesn't spam.

## 5. Prerequisite instrumentation (a separately authorized phase, before any fallback behavior)

Honest gap: the shipped Phase 5 data **cannot** measure serviceable demand
or the §7 metrics, because decisions do not capture the contemporaneous
alternative pool, `relay_sessions` is mutable, `select_session` overwrites
rather than records history, and `crossed_routes=0` is a fixture-authored
acceptance check, not a production metric. Therefore the implementation
plan starts with a **read-only instrumentation phase** (no fallback
behavior, separately authorized) delivering:

1. **Alternative-pool capture**: when a routing decision fails with
   `terminal_session`, record (inside the same explanation) whether a
   same-task successor existed at that instant, as an additional ineligible
   candidate (`not_selected_fallback_disabled`). This makes demand
   measurable prospectively.
2. **Selection history**: an additive, append-only `relay_selection_events`
   table recording every `select_session` (who, when, from→to), enabling
   the §7 "human re-routed within 24h" metric and authorization replay.
3. **Production route audit**: a scheduled read-only job asserting every
   routed envelope's binding matches a session the sender could access at
   routing time (the production analog of the fixture's `crossed_routes`),
   reported via the admin surface.
4. **Operator surfaces**: a reason-code filter on the Phase 5 admin views
   and a read-only CLI (`ostag routing fallbacks --since …`). Neither
   exists today; both are deliverables, not assumptions.

## 6. Evidence guarantee (stronger than Phase 5 best-effort)

Phase 5's best-effort recording is correct for *explanations of
human-driven routing*: losing an explanation must never break routing.
An **automatic** selection inverts the priority: a machine may not reroute
without evidence. Design rule:

> The `auto_fallback` RoutingDecision row is committed **in the same
> SQLite transaction** as the outbound envelope enqueue. If that
> transaction cannot commit, the fallback does not happen and the attempt
> fails closed (as today).

Best-effort recording remains for all non-automatic decisions. Zero
`explanation_error` decisions (§7) is a health signal, not the proof of
completeness — the transactional coupling is the proof.

## 7. Demand gate, canary population, and success metrics

**Demand gate** (measured only after §5 instrumentation has run):

- ≥ 30 consecutive days and ≥ 200 recorded decisions on the canary
  instance;
- ≥ 5% of decisions are `terminal_session` failures **where the captured
  alternative pool shows an eligible same-task successor existed**;
- zero `schema_mismatch` and zero `explanation_error` in the window;
- if demand is under threshold, the honest outcome is **do not build**.

**Canary**: an allow-list of `(principal, instance)` **pairs**
(`auto_fallback_canary`), default empty, initially exactly one pair (the
owner on one named instance). Both the principal and the instance must
match; all other traffic keeps fail-closed behavior.

**Window**: 14 days **and** ≥ 20 recorded `auto_fallback` decisions,
whichever is later.

**Success metrics** (all required to widen the canary):

- ≥ 90% of fallback decisions with no subsequent human re-route of the
  same task within 24h (measured from `relay_selection_events`);
- **zero** fallback decisions to a session the principal could not access
  at decision time (replayed from the recorded decision + selection
  history; any violation is an immediate kill);
- production route audit (§5.3) clean throughout; fixture acceptance
  `crossed_routes=0` maintained;
- completion governance shows no drop in evidence-backed completion rate
  for fallback-routed tasks vs. baseline.

## 8. Kill switch and rollback

- Settings are loaded once at startup in the current configuration model,
  so a config flag alone cannot deliver a no-restart kill. The kill switch
  is therefore a **DB-backed control row** (`auto_fallback_enabled` in the
  monitor store, default absent=off) read **per routing attempt** inside
  the same transaction as §6. Flipping it off takes effect on the next
  message with no restart; the config allow-list (§7) is a second,
  independent gate evaluated at the same point.
- Rollback = control row off. No schema rollback needed: fallback writes
  only additive rows (`routing_decisions`, `human_escalations`,
  `relay_selection_events`), all inert to routing by Phases 4–5 design.
- Automatic circuit breaker: 3 `auto_fallback` decisions for the same
  `(principal, task_id)` within 1 hour disables fallback for that pair for
  24h (recorded as a control row) and escalates (class `configuration`,
  audience `operator`).

## 9. Explicit owner approval gate

Implementation may begin only when the owner has explicitly approved, in
writing, ALL of:

1. the §5 instrumentation phase (itself a gated, read-only phase);
2. the observed demand-gate evidence (§7) — including the "do not build"
   outcome if demand is under threshold;
3. this design (or its amended version) as the implementation contract;
4. the canary pair list and duration (§7);
5. a new phase authorization naming the branch, reviewer, and verification
   matrix (same gate discipline as Phases 0–5).

Absent any one of these, no fallback selector may be implemented, flagged,
or scheduled. This document creates no obligation to build anything — the
demand test is allowed to conclude "no".
