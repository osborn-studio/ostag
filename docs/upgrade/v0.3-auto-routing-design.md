# Automatic routing fallback — design only (Phase 6)

**Status: DESIGN. Nothing in this document is implemented, flagged on,
scheduled, or deployed.** Phase 6 of the v0.3→v0.4 upgrade authorizes a
design document only (handoff §10). Any runtime change requires a new,
separately authorized phase gated on the explicit owner approval described
in §8 below.

## 1. What "automatic fallback" would mean in OStag

Today the relay router (`CopilotRelayService`) is deterministic with a
single candidate: the quoted envelope's session, else the principal's
current session. When that session is unusable (terminal, inaccessible,
stale), routing **fails closed** and a human re-selects. Automatic fallback
would let the router select an alternative session/device for a message
when the primary candidate is unusable — the capability upstream OpenTag
Phase 3 ships as its authoritative placement selector, which Phase 5
deliberately did not port.

Everything needed to do this safely already exists after Phases 1–5:

- **RoutingDecision** (Phase 5) records candidates, eligibility reasons,
  and the selected route for every decision — the audit substrate.
- **AgentAccessProfileSnapshot** (Phase 3) freezes who was allowed to reach
  what at intake — the authorization substrate.
- **HumanEscalation** (Phase 4) provides time-bounded, non-expiring-into-
  authorization human decisions — the escalation substrate.
- **CompletionContract** (Phase 1/2) distinguishes "agent responded" from
  "work completed with evidence" — the success-metric substrate.

## 2. Enable criteria and required Phase 5 observation window

Fallback may not be designed-in-the-dark; it must be justified by observed
Phase 5 data. All of the following before any implementation phase begins:

1. **Observation window:** ≥ 30 consecutive days of production
   `routing_decisions` on the primary instance, with ≥ 200 recorded
   decisions total.
2. **Failure evidence:** ≥ 5% of decisions in the window carry reason codes
   in {`terminal_session`, `no_current_session`, `stale_decision_version`}
   — i.e., real demand for fallback. If the failure rate is below that,
   fallback is complexity without benefit: **do not build it**.
3. **Explanation health:** zero `schema_mismatch` and zero
   `explanation_error` decisions in the window (the explanation layer must
   demonstrably represent every real outcome before it can be trusted to
   audit an automatic selector).
4. **Baseline integrity:** dual-device acceptance `crossed_routes=0`
   throughout the window; no unresolved cross-route incident.

## 3. Candidate constraints and deterministic preference order

Candidate pool for a fallback decision (all constraints AND-ed):

- sessions belonging to the **same principal** and the **same instance
  scope** the principal is already authorized for (`IdentityStore` bindings;
  never a broader scope than the failed primary);
- session state in {`running`, `awaiting_decision`, `idle`} (never terminal);
- session **task identity matches** the message context (same `task_id`
  when the message is a quoted decision answer; otherwise any active session
  of the principal);
- access-profile snapshot (Phase 3) for the target task, when present, must
  not be revoked or expired;
- write-gating unchanged: canary session allow-lists and
  `write_enabled` flags apply to the fallback target exactly as to a
  directly selected session.

Deterministic preference order (total order; no randomness, no load
balancing in v1):

1. same `task_id` as the failed primary, most recent `updated_at`;
2. same `instance_id` as the failed primary, most recent `updated_at`;
3. any eligible session, most recent `updated_at`;
4. tie-break on lexicographic `(instance_id, runtime_id, session_id)`.

The selector must be a **pure function** of (failed primary, candidate
rows, message context) so the RoutingDecision explanation reproduces it
exactly — the Phase 5 rule "selected equals the actual route" stays
byte-provable.

## 4. Failure and fallback semantics

- Fallback triggers **only** on the three demand codes above — never on
  `access_denied` (an authorization failure must stay a failure), never on
  policy gates (`requires_approval`/`requires_confirmation` outcomes are
  human gates, not routing failures), never on `duplicate_event`.
- **One hop.** If the fallback target also fails, the attempt fails closed
  and escalates; no cascading.
- Every fallback emits a `RoutingDecision` whose candidates include the
  failed primary (ineligible, with its real reason) AND the chosen target,
  plus a decision-level reason code `auto_fallback` (new vocabulary entry).
- Every fallback additionally opens a **non-blocking** Phase 4
  `HumanEscalation` (class `reconciliation`, audience `work_item_owner`,
  dedupe key `fallback:{task_id}`) so a human always sees that a machine
  re-routed — deduped so a noisy primary doesn't spam.
- Messages classified `requires_approval` are **never** eligible for
  fallback routing, even after approval — approved high-risk instructions
  go only to the explicitly selected session.

## 5. Canary population and success metrics

- **Canary:** one named principal (the owner) on one named instance, via a
  config allow-list (`auto_fallback_canary_principals`), default empty.
  Everyone else keeps fail-closed behavior.
- **Window:** 14 days minimum.
- **Success metrics** (all required to widen the canary):
  - ≥ 90% of fallback decisions resolved without the human re-routing the
    message within 24h (measured against subsequent `select_session` +
    resend patterns);
  - zero fallback decisions to a session the principal could not have
    selected manually (audited by replaying decisions against
    `IdentityStore` history — this metric at anything above zero is an
    immediate kill);
  - zero `crossed_routes` in the acceptance fixture and production audit;
  - completion governance (Phase 1) shows no drop in evidence-backed
    completion rate for fallback-routed tasks vs. baseline.

## 6. Kill switch and rollback

- Config flag `auto_fallback_enabled` (default **false**) checked on every
  routing attempt — flipping it off restores fail-closed behavior on the
  next message with no restart.
- The canary allow-list is a second, independent gate (both must pass).
- Rollback = flag off. No schema rollback is needed: fallback writes only
  additive `RoutingDecision`/`HumanEscalation` rows, both already inert to
  routing by Phases 4–5 design.
- An automatic circuit breaker: 3 fallback decisions for the same
  `(principal, task_id)` within 1 hour disables fallback for that pair for
  24h and escalates (class `configuration`, audience `operator`).

## 7. Audit evidence and operator controls

- Every fallback is fully reconstructable from `routing_decisions` (which
  candidate failed, why, what was chosen, under which preference rule —
  the rule index is recorded in the candidate reason message) plus the
  paired escalation row.
- Operator controls: admin views (Phase 5) filterable by
  `reasonCode=auto_fallback`; a CLI report
  (`ostag routing fallbacks --since …`) summarizing count, success metric,
  and circuit-breaker trips; both read-only.
- The audit path itself follows the Phase 5 contract: explanations are
  derived from what the selector actually did, recorded best-effort, never
  consulted by routing.

## 8. Explicit owner approval gate

Implementation may begin only when the owner has explicitly approved, in
writing, ALL of:

1. the observed Phase 5 window evidence (§2) — including the "do not build"
   outcome if demand is under threshold;
2. this design (or its amended version) as the implementation contract;
3. the canary population and its duration (§5);
4. a new phase authorization naming the branch, reviewer, and verification
   matrix (same gate discipline as Phases 0–5).

Absent any one of these, the fallback selector must not be implemented,
flagged, or scheduled. This document creates no obligation to build it —
the §2 demand test is allowed to conclude "no".
