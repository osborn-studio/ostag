## 6. Recorded compatibility decisions (handoff §5.2 / §0.3 — resolved, not silent)

1. **Multiple run results — scoped precisely (review r1 correction):** the `task_id == run_id` identity holds **only on the work-monitor reporter projection path** (`work_monitor/reporter.py:388`). It is *not* a repo-wide invariant: relay contracts model session/turn independently (`copilot_relay/models.py:124`), and `work_monitor/executor.py:213` **replaces** the tracked run when a newer osstack attempt appears (attempt-aware, latest-only). Decision: (a) the Phase 1 evaluator takes `run_results: list` (N≥1, upstream-shaped) with the **caller** responsible for aggregation; (b) the legacy-equivalence claim is asserted **only** for the `core/runner.py` → `run_ledger.record_status` path, where exactly one run result exists per run — and is covered by a regression test on that path only; (c) aggregation of multiple attempts into one work-thread's `run_results` (executor replacement scenario) is explicitly **deferred to Phase 2 integration**, with a dedicated test that a newer attempt *appends* rather than overwrites once wired. No existing behavior changes in Phase 1.
2. **`crossed_routes` provenance:** the acceptance value is **authored in fixtures** (`tests/fixtures/multi-device/*.json`), validated — not computed — by `scripts/multi_device_copilot_acceptance.py`; live measurement is a manual operator procedure (`docs/operations/copilot-relay.md`). The deterministic gate for this upgrade is therefore *"fixture acceptance **exits 0 and prints `status=passed … crossed_routes=0`**"* — the osstack spec runs it under `pipefail` so the script's own exit status can never be masked by the grep (review r1 correction). Plus the guardrail that no phase touches routing code paths in a way that would invalidate the manual procedure. A computed metric is future work (candidate for Phase 6 doc).
3. **"Personal board" mapping + work-thread identity (review r1 correction):** the handoff's employee/admin language maps onto OStag's real scoping: `personal` = principal-bound device scope (`status_board._allowed`), `admin/team` = global-owner scope. Because tasks are keyed by **`(instance_id, task_id)`** (`work_monitor/store.py:42`) and personal authorization filters by instance/device, completion-governance records MUST carry the instance dimension: `work_thread_id := "{instance_id}/{task_id}"` **and** a dedicated `instance_id` column on every completion table, so all scoped reads join through the existing authorization filter. A completion record is never queryable by `task_id` alone. Phase 2 builds `WorkLoopView` behind this **existing** boundary; a non-leakage test (employee A cannot read employee B's instance's completion rows) is a Phase 1 acceptance item, not just Phase 2.
4. **`assessedBy` attribution:** OStag will emit `"ostag" | "human"` (native divergence from upstream `"opentag" | "human"`), declared in the Phase 1 mapping note + compatibility test, per handoff §5.1.
5. **Persistence strategy for Phase 1 (review r1 completion):**
   - **Layering:** the evaluator is a pure function (no IO). Persistence sits behind a small repository interface.
   - **SQLite is the source of truth** for governance records, via `MonitorStore.MIGRATIONS` (additive `user_version` bump): four tables — `completion_contracts`, `completion_evidence` (immutable facts), `completion_waivers` (first-class rows: id, contract id/version, cycle, **optional run_id** (upstream `CompletionWaiver.runId`), actor, reason, scope, policy_scope, gate_ids JSON, waived_at, expires_at; **not** embedded JSON), `completion_assessments` (append-only, `UNIQUE(instance_id, work_thread_key, sequence)` + `input_digest` for the `recorded|duplicate|conflict` optimistic append). Every table carries `instance_id` (decision §6.3).
   - **Monitor-disabled mode:** the runner can operate without a `MonitorStore` (`ostag/main.py:423,824`). In that mode nothing changes from today: the legacy path writes terminal status to the JSONL run ledger only, and Phase 1 wraps it as an **in-memory** `execution_compat` assessment mirrored to a `completion_assessed` ledger event (best-effort JSONL, same durability as today's `record_status`). `governed`-mode contracts **require** a `MonitorStore`; configuring governed completion without one is a validated startup error, never a silent downgrade.
   - **Partial-failure rule:** SQLite commit first; JSONL mirror best-effort afterwards (identical to the existing `record_status` durability). Recovery = SQLite replay; the mirror is audit convenience, never read back for decisions.
