# OStag 卡点复盘与交付重排（2026-09-18）

结论：主要问题是执行顺序失衡。代码持续增加，但会议准备这条用户流程没有完成。我把生产治理和故障边界的完善排到了首个可用会议包之前，每轮完成基础设施后又增加新的前置条件。这是我需要纠正的推进方式，不能用测试数量替代产品交付。

## 已核对的事实

- 计划版本起点到本次诊断前，共 73 个提交；这个数包含队列、文档和代码，不是 73 项功能。
- 最近 A11a–d 四轮分别实现状态、权限快照、本地操作记录和控制状态桥接，都是不同代码，但没有交付双源会议内容；四次 osstack 编码/验证运行合计约 128 分钟，尚不含任务间等待。不能据此推算整个项目总工时。
- 这四轮有 12 个提交，其中 4 个是产品代码提交，另外是队列和证据文档。每一轮都以 A11 仍部分完成结束，缺少直接面向用户的终止标准。
- `DEVELOPMENT-START.md` 承诺第一项验收是合成飞书材料与 GitHub 事实生成会议包，却把大段 A 系列运行基础设施放在前面。计划本身就存在目标与顺序不一致。
- `execution.json` 的活动指针一直指向 A11；原始 `backlog.json` 是 40 项计划快照，全部仍标 planned，不能直接把它当动态进度表。旧开发入口和执行历史又包含不同阶段的“最新”，增加了恢复上下文时的误判。

## Claude Fable 5.1 的独立判断

已实际调用 `/opt/homebrew/bin/claude`，请求 `claude-fable-5-1`；响应 modelUsage 确认该模型处理主诊断。Fable 使用我提供的计划、进度与历史，未读取源码、执行测试或验证生产环境。原始诊断保留，下面是主要意见的归纳：

1. 横向基础设施工作挤占纵向交付；原计划在同一页写下会议包目标，又将其推后。
2. A11 范围不断扩张，甚至包含 D02 的部署前置检查；缺少关闭条件会导致无限细分。
3. 多轮全量测试和模型审查确有成本，但主要瓶颈是每轮又生成新的 pending 前提。不能把责任推给审计模型或测试本身。
4. 单次离线会议预览无需运行 worker、发送卡片或执行部署，所以不需要先完成生产排空协议。真实权限、来源和费用边界在以后接入真实数据/模型时仍必须落实。
5. 立即交付本地、合成、只读会议包命令，以合并/部署区分、缺口、歧义和来源引用作为验收内容。

我对其中两点作收敛：不能仅凭文件记录断言从未重复修过同一 bug；更准确的判断是已明确观察到同一安全主题在多层重复展开。也不能笼统说单次运行不会遇到撤权；本轮采用合成材料、无网络/模型/投递，才不需要生产授权更新器。真实数据路径必须另行验证当前权限。

## 是否在重复

重复的是推进模式和主题：当前权限检查、在途/排空证明、不确定发送、故障关闭在 service、worker、卡片、状态和控制边界逐层展开。多项修复确有独立价值；问题是没有用户流程将它们组合起来并形成反馈。后续禁止没有具体触发场景的新一层加固自动成为下轮任务。

本轮也暴露了同类问题没有一次覆盖完整：第一次只修了类型化版本标识符被隐藏，第二次审查又发现普通中文版本号会被同一链接过滤规则整段删除。旧问题确实修复，但正常中文样本不足导致修复范围偏窄；不能把这全部解释成“不同安全边界”。已增加保留目标、标题、数字和 PR 引用的正常中文回归，防止只测危险输入、忽略内容可用性。

| 后续扩展 | 受控写回、例行任务、销售与其余上游能力 | 按原独立发布条件推进，不再阻塞首个会议准备流程 |

本轮停止继续细拆 A11e；不取消已经实现的保护。R1 不启用任何生产开关，不发送消息，不接触业务数据库。只接受明确标注的合成输入；标记仅表明用法约定，不证明内容确为虚构。真正面向公司的功能完成仍以 R2/R3 验收为准。

每轮先明确用户能运行什么和看到什么；满足该增量的行为测试后，仅修复与其范围有关的实际问题。不得为了假设中的未来生产场景无限追加前提。离线渲染改动不重复执行不相关的双 OS/26 组网络与生命周期探针；既有完整生产检查在发布阶段保留。
